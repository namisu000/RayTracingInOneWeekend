## 뷰포트 용어를 이해한 과정

### ① 뷰포트를 왜 카메라 앞에 수직으로 세울까?
- **처음 생각**: 왜 직교하지? 그렇게 설계한 것. 핀홀 카메라가 그렇게 생겨서. 센서가 뷰포트, 렌즈가 카메라? 반대인듯 (초안)
- **정리**: 대응 관계는 처음 생각이 맞았다 (핀홀 = 카메라 중심, 센서 = 뷰포트). 수직으로 세우면 카메라가 뷰포트 중심을 정면으로 봐서 화면이 상하좌우로 대칭이 된다.

### ② 뷰포트 크기는 무엇을 의미할까?
- **처음 생각**: 뷰포트는 실수 세계의 무한한 점들이고, 비율만 나타내기 때문에 거기서 몇 개를 샘플링할지가 이미지 해상도다 (대화). 스마트폰 줌은 뷰포트 높이 ÷ `focal_length`, 즉 시야각만 변한 것이다 (초안).
- **정리**: 뷰포트는 실제 크기가 있지만 그 숫자 자체에는 의미가 없다. 의미 있는 건 비율 두 개다. 시야각을 정하는 `높이 / focal_length`와 가로세로 비율인 `너비 / 높이`. 초안에서 이미 시야각 비율까지는 도달해 있었다.

### ②-1 viewport_width를 계산할 때 aspect_ratio를 왜 안 쓸까?
- **처음 생각**: `image_width`, `image_height`는 `int`로 변환된 값이라 실제 비율과 다를 수 있어서 (코드 주석, 스스로 묻고 답함)
- **정리**: 맞다. 덧붙이면 비율이 어긋나면 픽셀이 정사각형이 아니게 된다.

### ③ upper_left, viewport_u, viewport_v는 왜 이렇게 정의할까?
- **처음 생각**: 중심에서 u/2, v/2를 빼서 upper_left를 구한다. `viewport_v`는 아래 방향이라 빼면 위로 올라간다 (코드 주석). 계산 방법은 알았지만, v를 **왜** 아래로 두는지와 u, v가 변의 길이까지 담는다는 건 생각하지 못했다. 초안에 "이미지 Y축은 뒤집혀 있다"를 적어 놓고도 v와 연결하지 않았다.
- **정리**: 이미지 스캔 순서(왼쪽 위에서 시작, 아래로 갈수록 행 번호 증가)와 맞추려고 v를 아래로 둔다. u, v가 변 전체 길이라서 `upper_left + s·u + t·v`로 뷰포트 위의 아무 점이나 가리킬 수 있다.

### ④ pixel_delta는 무엇일까?
- **처음 생각**: 픽셀 간격. 이미지 해상도는 뷰포트를 몇 칸으로 나눌지만 결정한다 (코드 주석).
- **정리**: 맞다. 해상도가 처음 등장하는 곳이고, 해상도를 올리면 칸만 촘촘해진다.

### ⑤ pixel00_loc은 왜 칸의 중심일까?
- **처음 생각**: (0, 0) 픽셀 칸의 중심 (코드 주석). 무엇인지는 알았지만 **왜** 중심을 쓰는지는 생각하지 못했다.
- **정리**: 모서리를 쓰면 첫 픽셀은 왼쪽 끝에 붙고 마지막 픽셀은 오른쪽 끝에서 한 칸 모자라서, 그림이 반 칸 치우친다. 중심을 써야 양 끝에서 반 칸씩 떨어져 대칭이 된다.

## ray 방향과 정규화

### ray 방향을 정규화해야 할까?
- **처음 생각**: 당장은 맞닿는 지점만 계산하니까 필요 없지 않나? 하지만 나중에 정말 방향 성분으로 쓰일 때는 정규화하지 않을까.
- **정리**: 둘 다 맞다.
  - ray를 만들 때는 정규화하지 않는다. `ray_direction = pixel_center - camera_center`를 그대로 저장한다.
  - 교차점만 구할 때는 방향의 길이가 상관없다. `A + t·b`와 `A + (t/2)·(2b)`는 같은 점이고, `t` 값만 달라진다.
  - 방향 성분이 필요한 곳에서 그때 정규화한다. 지금은 `ray_color`, 나중에는 굴절(Dielectrics)에서 `unit_vector(r_in.direction())`
  - 주의: 방향이 단위 벡터가 아니면 `t`는 거리가 아니다. `t > 0.001` 같은 조건은 월드 거리 0.001이 아니라 "방향 벡터 길이의 0.001배"라는 뜻이다.

### 코드에서 실제로 정규화하는 곳이 있나?
- **처음 생각**: 실제 예제 코드에서는 정규화하지 않는 거 아닌가?
- **정리**: ray 자체는 정규화하지 않는 게 맞다. 대신 `ray_color`의 첫 줄에서 복사본을 정규화한다.
  ```cpp
  vec3 unit_direction = unit_vector(r.direction());   // main.cpp

  inline vec3 unit_vector(const vec3& v) {             // vec3.h
      return v / v.length();                           // 자기 길이로 나눔 → 길이 1
  }
  ```
  - `r`의 `dir`은 그대로 두고, 길이 1인 새 벡터를 만든다.

### 가로 그라데이션은 왜 생길까?
- **처음 생각**: 배경에 가로 그라데이션이 생기는 건 당연한 거 아닌가? 크기는 y 값으로만 결정되는 게 아니다.
- **정리**: 세로 그라데이션은 당연하지만, 한 행 안에서 좌우로 색이 바뀌는 건 정규화 때문에 생기는 부수 효과다.
  - 정규화된 y = `unit_direction.y()` = `y / √(x² + y² + 1)`
  - 같은 행은 y가 같지만, 가장자리로 갈수록 x가 커져서 분모가 커진다. 그래서 정규화된 y가 0에 가까워진다.
  - 맨 윗줄(y = 1) 예시:

    | 위치 | x | 정규화된 y | a |
    |---|---|---|---|
    | 가운데 | 0 | ≈ 0.71 | ≈ 0.85 (더 파람) |
    | 가장자리 | ±1.78 | ≈ 0.44 | ≈ 0.72 (더 흼) |

  - 정규화하지 않고 `r.direction().y()`를 쓰면 한 행이 전부 같은 색이 된다. 순수하게 세로 그라데이션만 생긴다.
  - 정규화 때문에 색 띠가 살짝 휘어진 곡선이 된다. 윗부분은 가운데가 더 파랗고, 아랫부분은 가장자리가 더 파랗다.

### y의 범위가 -1 ~ 1인 이유는?
- **처음 생각**: ray가 애초에 뷰포트 안에서만 정의되니까, ray의 범위가 뷰포트에 제한되는 거구나.
- **정리**: 반만 맞다. 이유가 두 가지 섞여 있었다.

  | | 범위 | 이유 |
  |---|---|---|
  | 정규화 전 `r.direction().y()` | -1 ~ 1 | `viewport_height = 2.0`이라 뷰포트가 y = -1 ~ 1에 걸쳐 있음 (우연) |
  | 정규화 후 이론상 범위 | -1 ~ 1 | 단위 벡터는 `x² + y² + z² = 1`이라 어떤 성분도 1을 넘을 수 없음 |
  | 정규화 후 이 카메라에서 실제 범위 | 약 -0.71 ~ 0.71 | ray가 전부 뷰포트를 지나서, 정확히 위나 아래를 보는 ray는 없음 |

  - 코드의 `0.5 * (y + 1.0)`은 이론상 범위(-1 ~ 1)를 가정한 것이다. 어떤 카메라에서든 `a`가 0 ~ 1에 들어오게 하려고.
  - 뷰포트 제한은 "실제로는 더 좁다"의 이유다. 이 카메라에서는 `a`가 대략 0.15 ~ 0.85만 쓰여서, 완전한 흰색이나 하늘색은 나오지 않는다.

### 정규화하면 y가 왜 작아질까?
- **처음 생각**: 정규화하면 길이가 1이 돼서 y도 같이 작아지는 거군.
- **정리**: 맞다.
  - 세 성분이 모두 같은 비율로 줄어서 y도 같이 작아진다.
  - 예) 정규화 전 `(0, 1, -1)` → 길이 √2 ≈ 1.41, y = 1
  - 정규화 후 `(0, 0.71, -0.71)` → 길이 1, y ≈ 0.71
  - 가장자리 픽셀은 x 성분까지 있어서 원래 길이가 더 길다. 그만큼 더 큰 수로 나누니까 y가 더 많이 줄어든다. 이게 가로 그라데이션의 이유다.

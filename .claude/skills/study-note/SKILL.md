# 학습 노트 만들기

사용자가 쓴 초안을 바탕으로 챕터 정리본을 만든다. 작성 방식의 전체 설명은 `notes/README.md`에 있다. 이 스킬과 README가 어긋나면 사용자에게 알린다.

- 교재: https://raytracing.github.io/books/RayTracingInOneWeekend.html
- 인자: 챕터 번호 (예: `5`). 초안은 사용자가 메시지에 붙여넣는다. 초안이 없으면 먼저 달라고 한다.

## 원칙

- **정리본의 뼈대는 사용자의 초안이다.** 초안의 순서, 내용, 말투(`~다` 체 메모)를 따른다. 새 구조를 짜지 않는다.
- **사용자가 요청하지 않은 내용을 정리본에 몰래 넣지 않는다.** 추가하면 좋을 내용은 채팅으로 제안하고, 사용자가 원할 때만 넣는다. 예외: 코드 주석에 이미 있는 내용, 초안에서 제목만 있고 비어 있는 부분.
- **틀린 이해는 고치되, 초안은 그대로 둔다.** 틀렸다가 고친 흔적은 `drafts/`와 정리본을 비교하면 보이게 한다.
- **용어를 나열하지 말고 "왜 이렇게 정의되는지"를 쓴다.** 목표에서 출발해서 각 개념이 왜 필요해지는지 흐름으로 설명한다.
- AI가 한 일을 사용자가 한 것처럼 쓰지 않는다 (README의 투명성 원칙).

## 이름 규칙

| 종류 | 파일 | 제목(H1) |
|---|---|---|
| 초안 | `notes/drafts/ch<NN>-draft.md` | 달지 않음 (원문 그대로) |
| 사고 과정 | `notes/thinking/ch<NN>-thinking.md` | `# Ch N. <책의 챕터 제목>: 사고 과정` |
| 정리본 | `notes/ch<NN>-note.md` | `# Ch N. <책의 챕터 제목>` |

- `<NN>`은 두 자리 챕터 번호다 (`ch04`, `ch10`). 파일 정렬 순서를 맞추기 위해서다.
- 제목 안의 챕터 번호는 한 자리 그대로 쓴다 (`Ch 4.`).
- 정리본의 소제목은 책의 절 번호를 따른다 (`## 4.1 The ray Class`).

## 순서

### 1. 초안 저장
`notes/drafts/ch<NN>-draft.md`에 초안을 **글자 그대로** 저장한다. 오타, 잘못된 이해, "(왜지?)" 같은 메모도 고치지 않는다.

### 2. 자료 모으기
- 책의 해당 챕터 내용 (WebFetch)
- 이 챕터의 코드와 주석: `git log --oneline`에서 `ch <N>` 커밋들을 찾고, 관련 파일(`RayTracingInOneWeekend/*.cpp, *.h`)의 주석을 읽는다.
- `notes/src/`에서 이 챕터용 이미지를 확인한다. 이미지는 Read로 직접 본다.

### 3. 검토 결과를 채팅으로 보고
정리본을 쓰기 전에 아래 항목을 채팅으로 먼저 보여준다.
1. **틀리거나 부정확한 부분**: 초안 문장을 인용하고, 왜 틀렸는지 설명한다. 코드 주석도 검사한다.
2. **주석 반영 여부**: 코드 주석마다 초안에 들어 있는지 표로 보여준다.
3. **추가하면 좋을 부분**: 책에는 있는데 초안에 없는 중요한 내용
4. **모호한 부분**: 비유나 설명이 정확하지 않은 곳

### 4. 정리본 작성
`notes/ch<NN>-note.md`에 쓴다 (예: `ch04-note.md`).
- 제목 바로 아래에 `> [초안](drafts/ch<NN>-draft.md) · [사고 과정](thinking/ch<NN>-thinking.md)` 링크를 단다.
- 제목: `# Ch N. <책의 챕터 제목>`, 소제목은 책의 절 번호를 따른다 (`## 4.1 The ray Class`).
- 오타를 고치고, 틀린 부분은 바로잡은 내용으로 쓴다.
- 코드 주석의 내용을 해당 위치에 녹인다. 관련 코드 조각을 같이 넣는다.
- 이미지는 `![설명](src/파일명.png)`로 넣고, 바로 아래에 그림 속 개념이 왜 그렇게 정의되는지 설명한다.
- 한국어로 쓰고, 영어 용어는 코드 이름이나 널리 쓰는 용어만 그대로 둔다.

### 5. 사고 과정 정리 (후속 질문이 있을 때)
사용자가 노트를 보고 질문하면 답한 뒤, `notes/thinking/ch<NN>-thinking.md`에 남긴다. **정리본에는 Q&A를 넣지 않는다.**
- 사고 과정 파일: 질문마다 이 형식으로 쓴다.

  ```markdown
  ### <질문을 한 줄로>
  - **처음 생각**: 사용자가 처음에 어떻게 이해했는지 (사용자 말을 최대한 살리고, 출처를 괄호로: 초안 / 코드 주석 / 대화)
  - **정리**: 결론. 처음 생각에서 맞은 부분과 틀린 부분을 구분한다.
  ```

- 정리본: 질문에서 나온 결론만 해당 위치에 일반 설명으로 녹이고, 사고 과정 파일로 가는 링크를 단다.
  `> 이 부분을 이해한 과정은 [사고 과정](thinking/ch<NN>-thinking.md#앵커)에 있다.`
- 대화를 통째로 옮기지 않는다. 질문 하나당 "처음 생각 → 정리"만 남긴다.
- 처음 생각을 메모에서 추정해야 할 때는 먼저 채팅으로 보여주고, 사용자가 확인한 뒤에만 쓴다.

### 6. 마무리
- `notes/README.md`에 새 챕터에서 틀렸다 고친 사례가 인상적이면 예시 표에 추가할지 사용자에게 묻는다.
- 커밋 메시지를 추천한다 (예: `add ch 5 study note`). 커밋은 사용자가 요청할 때만 한다.

## 마크다운 주의

- ❌ `**텍스트(ASCII)**로`
